# Автоматический сбор аккаунтов

### Автоматическая регистрация аккаунтов на станциях

`scripts/harvest_accounts.py` повторяет ручной цикл Босса целиком: взять следующий свободный
GitHub-аккаунт, открыть партнёрскую ссылку станции, войти через GitHub OAuth (регистрация
у New API происходит сама на первом входе, отдельной формы нет), создать API-ключ, снять
его полное значение, забрать «Токен доступа» и «ID пользователя» с профиля и записать всё
в базу через backend.

    uv run python scripts/harvest_accounts.py [домен] [--count N] [--dry]
                                              [--github <id>] [--inviter <id>]

Отчёт — `log/harvest.txt`, кроном не запускается: это разовые пачки по решению Босса.
Один прогон одной головы — 1.5-2 минуты живого браузера.

Разлогиниваться в GitHub не нужно: каждый аккаунт идёт **в своей сессии agent-browser**,
где GitHub не залогинен и сам показывает форму входа, а рабочий Chrome Босса не трогается.
Код подтверждения устройства GitHub спрашивает примерно у половины аккаунтов (при заходе
с нового IP) — `fetch_device_code()` из чек-ина достаёт его из ящика, это рутина, а не сбой.

**Ключ снимается запросом, а не кнопкой.** Полное значение New API не отдаёт нигде, кроме
`POST /api/token/<id>/key` (у GET на этом пути «Invalid URL») — путь подсмотрен перехватом
`XMLHttpRequest.prototype.open`: SPA ходит через XHR, поэтому подмена `window.fetch` ничего
не показывала. Запасной путь `key_by_clipboard()` остался: он открывает `/keys`, подменяет
`navigator.clipboard.writeText` и жмёт безымянную кнопку-иконку рядом со строкой ключа
(искать её по слову «копировать» нельзя, текста у неё нет). Снятое сверяется с маской
панели по краям (`masked_match`) — кнопок на странице столько же, сколько ключей.

Все запросы к панели идут **изнутри страницы**, под её cookie-сессией (`api()` через
`fetch` в `eval`): по Bearer панель отдаёт ключ только маской. Заголовок `New-Api-User`
берётся из `localStorage.user`.

**Прокси обязателен и только американский.** Пул — `HARVEST_PROXIES` в `.env`, формат
продавца `host:port:user:pass` принимается как есть; один аккаунт получает один адрес
на всю сессию, по кругу. GitHub с британского адреса не открывает даже свою страницу
(Cloudflare), а десятки разных логинов с одного IP он считает подозрительными, и пул
аккаунтов у Босса единственный.

Партнёрская ссылка берётся у конкретной записи-инвайтера (`INVITER`, на gorouter это
аккаунт 80): 40 $ за голову должны капать на одну запись, а не размазываться по всем.

Слабое место, оплаченное потерей трёх аккаунтов 25.08: аккаунт на станции создаётся раньше,
чем запись в базе, и при недоступном backend ключ с токеном доступа существуют только
в памяти прогона. Поэтому `render()` печатает токен доступа у всех незаписанных строк —
иначе повторно его взять нечем, панель отдаёт токен лишь своей cookie-сессии. По той же
причине отчёт пишется **после каждой головы**, а не в конце прогона, и вторым файлом
дописывается в `log/harvest_history.txt`: `harvest.txt` перезапишет следующий прогон крона,
а снятый ключ невосстановим.

#### Автономность под кроном

В кроне — `4,19,34,49 * * * *` (`--count 15`), вывод в `log/harvest_cron.txt`: четыре
прогона в час, потолок около 50 голов — ровно цель Босса. Отсюда два требования: прогон
не должен падать ни от чего и не должен застревать на одном аккаунте.

Неудачный аккаунт получает второй заход (`ATTEMPTS = 2`) **с другого адреса пула**
(`proxy_order()`): отказал не ящик, а адрес — письмо GitHub недосылает без всякой связи
с почтой, зато к IP придирчив. Провалившийся адрес назван в логе строкой «адрес … не
пустил, пробую с другого». Повтор идёт только на статусах `RETRY_STATUSES`
(`НЕ ВОШЁЛ`, `ОШИБКА`) — во всех прочих отказах аккаунт на станции уже создан, и второй
заход завёл бы ему второй ключ.

После неудачи аккаунт просто **пропускается**: ни пометок в базе (`error_status`
и `active` не трогаются вовсе), ни отсрочек, ни файла состояния. Отсрочки были и сняты
по решению Босса: GitHub не привязывает недоставку кода к конкретному ящику, откладывать
за это ящик бессмысленно. Вместо памяти о неудачниках — **случайная выборка**
(`random.sample` в `free_github()`): выборка по `id` каждым прогоном упиралась бы в одну
и ту же голову, а десятки заходов в сутки на один логин GitHub примет за перебор пароля.
Аккаунт, у которого запись на станции есть, а в базе нет, получает в отчёт пометку
«дописать в базу руками» — автоматике туда ходить нельзя.

Ни один сбой не выходит наружу: `harvest_one()` оборачивает заходы, `run_one()` — своё,
`save_report()` глотает ошибку записи, обращения к базе идут через `retry_db()` (три
попытки), а точка входа ловит остаток и печатает причину строкой (под кроном трейсбек
читать некому). Дедлайн прогона — `MAX_MINUTES` (13, флаг `--minutes`): голова занимает
около минуты, а прогон обязан кончиться сам, освободив место следующему; при шаге крона
15 минут пятнадцать голов по 32 с укладываются в восемь, остаток запаса идёт на отказные.
Наложения прогонов при этом не страшны: `hold_lock()` из
`scripts/single.py` заставляет второй экземпляр выйти молча. Пустой `HARVEST_PROXIES` —
отказ на старте: с домашнего адреса GitHub положит единственный пул аккаунтов.

#### Очередь недописанных голов

Аккаунт на станции создаётся раньше записи в базе, поэтому при лежащем backend ключ
и «токен доступа» существуют только в памяти прогона. 26.08 так пропало девять голов
по 70 $ из пятнадцати: панель их завела, а база не увидела — вернули руками из
`log/harvest_history.txt`. Больше терять нечего: голова, чью запись backend не принял
по молчанию, уезжает в `log/harvest_pending.json` (`pending_add`) и получает статус
`ОТЛОЖЕН`, а следующий прогон **начинает** с того, что дописывает очередь
(`pending_flush()` до выборки голов) — прямое требование Босса: сперва порядок в том, что
уже снято, и только потом новые аккаунты.

Молчание backend и отказ по делу разведены (`post_account` возвращает `True` / `None` /
`False`): таймаут и Connection refused лечатся повтором, а 409 и 400 — нет, и такая голова
висела бы в очереди вечно, поэтому выбрасывается. Если backend не ответил на первой же
голове очереди, прогон не берёт новых вовсе: остальные всё равно лягут в ту же очередь,
а каждая попытка стоит до 30 с таймаута. Дедуп в очереди по паре сайт + `github_id` —
голова могла пойти на второй заход и завести второй ключ, в базу нужен последний снятый.

`ОТЛОЖЕН` считается **удачной** головой и в отчёте, и в замере темпа (`GOOD`
в `harvest_speed.py`): аккаунт на станции есть, деньги наши, не доехала одна строка.
Пометку «дописать в базу руками» получают только статусы, где автоматике ходить нельзя.

Тесты на ротацию адресов — `tests/test_harvest_proxy.py`. Автономность (ретрай с другого
адреса, пропуск, исключение вместо падения) прогонялась 2026-08-26 на подставном
`run_one`: упавшая голова становится строкой отчёта, прогон доходит до конца списка
и возвращает 0.

#### Темп: голова за минуту, головы по одной

Цель Босса — 50 голов в час, то есть чуть больше минуты на голову. Замер по журналу
(шесть подряд удачных голов прогона 26.08 06:34) дал 99-105 секунд, и разложился он так:
старт → форма входа 39-41 с, форма → «требует код» 7 с, код из ящика 7-19 с, ввод кода →
Authorize 29-30 с, Authorize → dashboard 11-29 с, всё остальное 2-3 с. То есть съедали
время не сны, а ожидания переходов.

**Ждём `load`, а не `networkidle`** (`READY`): `networkidle` требует полутора секунд полной
тишины в сети, а SPA станции и GitHub всё это время что-то подтягивают — отсюда 20-30 с
на переход при уже готовой странице. `load` возвращается по готовности документа,
а недорисованную страницу добирает сам цикл `oauth_register`: он переспрашивает снимок
каждые `STEP` секунд, а где нужен конкретный текст — стоит явное `wait --text`. Итераций
цикла поэтому 20, а не 14: шагов у OAuth меньше, но часть уходит на добор.

**Письмо GitHub ждём по формуле Босса**: три взгляда в ящик с шагом `CODE_STEP` (4 с),
затем один «Re-send the authentication code», затем ещё три взгляда — и голова
пропускается. Обычно код приходит за пять секунд; бомбить ящик ресендами и десятком
опросов нельзя, а ждать незачем — выборка случайная, и в другой раз этот аккаунт пройдёт
с первого захода. Доступы ящика кэширует `mailbox()` (один поход в `main_email` на прогон),
взгляд делает `read_code()` через Graph напрямую: прежний `fetch_device_code()` из чек-ина
спал по 6 с и перечитывал строку базы перед каждой попыткой.

**Замок GitHub ретраем не обходится** (`LOCK_MARKS`, `locked()`): текст «There have been
several failed attempts to sign in from this account or IP address» привязан не только
к адресу, но и к логину — 26.08 аккаунт 311 получил его с двух совершенно новых адресов.
Такая голова не идёт на второй заход и не помечается в базе: замок снимается временем.

**Отказ станции от вины адреса отличается** (`STATION_MARKS`, `station_fault()`, статус
`ОТКАЗ СТАНЦИИ`): когда станция не начала OAuth вовсе — `/api/oauth/state` отдаёт nginx 500
или кнопки GitHub нет на странице, — до GitHub дело не дошло, и второй заход с другого прокси
меняет ровно ничего, стоя при этом полторы минуты живого браузера. Прогон tabitoken 27.08
дал 9 таких строк, и каждая получила бесполезный повтор: снаружи это выглядело как «GitHub
сопротивляется», хотя замков и 429 не было ни одного. Пометки «дописать в базу руками» такая
голова тоже не получает — аккаунта на станции нет.

Параллельности нет и не будет — прямое решение Босса: пять сессий сразу быстрее приведут
к бану, а одна голова в минуту нас устраивает.

Письмо ищется в окне `CODE_WINDOW` (90 с) от начала ожидания: у головы, пошедшей на второй
заход, в ящике лежит письмо первого, и с окном в минуты подставился бы его код. Радикальный
путь — чистить ящик `delete_mail_by_subject` перед заходом, но это два лишних похода в Graph
на голову, и без нужды он не применяется.

#### Замер темпа: `scripts/harvest_speed.py`

Отчёт говорит, что вышло, журнал — когда каждый шаг случился, а вопрос «правка ускорила или
замедлила» не закрывает ни один из них. `scripts/harvest_speed.py` разбирает журнал на прогоны
и головы, раскладывает время удачной головы по этапам OAuth и группирует прогоны по версии
темпа. Пишет `log/harvest_speed.txt`; зовётся сам в конце прогона сбора и руками:

    uv run python scripts/harvest_speed.py [число прогонов]

Версия темпа — константа `VERSION` в `scripts/harvest_accounts.py`, она уезжает в строку
старта журнала (`верс. 2`). Поднимать её при каждой правке ожиданий и пауз: без метки
сравнивать пришлось бы по времени суток руками, а прогоны старой и новой версии в журнале
лежат вперемешку. Прогоны без метки считаются первой версией.

Замер медианой, а не средним: одна застрявшая голова иначе перечёркивает картину прогона.
Второй заход той же головы приписывается к ней же — Боссу важно, сколько всего съел аккаунт.
Итог правок 26.08 (версия 1 → 2): удачная голова 104 с → 32 с, отказ 723 с → 135 с,
темп 18 → 36 в час.

#### Журнал прогона

`log/harvest_journal.txt` — построчный ход дела со временем каждого шага (`note()`,
формат `26.08 06:11:05`). Отчёт показывает итог, а журнал отвечает на вопрос «почему
встал»: разница между «не пустил» и «застрял» видна только по паузе между строками.
Дописывается вечно, подрезается до `JOURNAL_KEEP` (20000) строк при размере больше 4 МБ.

Шаги головы попадают туда сразу, а не пачкой в конце: список `log` внутри `run_one` — это
`Journal(list)`, чей `append` заодно пишет в журнал. Иначе все строки головы получили бы
одно время — время её конца.

Что пишется: выбранные головы списком `id/login` (выборка случайная, иначе не понять, шла
ли речь об одном аккаунте два прогона подряд), по каждой — адрес прокси и ящик, затем
дословные ответы GitHub (`github_says()`) и станции (`station_says()`), код и баланс.
Дословно, а не пересказом: «several failed attempts … from this account or IP address»
и «Incorrect username or password» лечатся по-разному. Экран device verification жалобой
не считается — он логируется своей строкой.

Код ответа панели тоже идёт в журнал (`api()` возвращает `__code` вместе с телом): **429
у станции — то, ради чего это заведено**. По времени между такими строками видно окно
лимита регистраций с одного адреса, а без кода 429 выглядел бы как «панель ответила
не JSON». Строка вида `станция: POST /api/token → 429 …`.

Строка `GitHub пропустил без вопросов, OK` означает, что ни формы входа, ни кода, ни
Authorize не было — сессия вошла сразу.

### Сбор по почте, без браузера и без GitHub

`scripts/harvest_email.py` делает то же, что `harvest_accounts.py`, но там, где станция пускает
по обычной паре логин-пароль и не включила капчу: тогда весь цикл — четыре HTTP-запроса,
голова занимает 15-20 секунд вместо минуты, прокси не нужен вовсе, а топливом идёт пул
`main_email`, а не GitHub. Это и есть **второй сбор**: GitHub-головы остаются главному —
станциям с opus-5 под мою сессию (gorouter, tabitoken), а картиночные берутся почтой.

    uv run python scripts/harvest_email.py [домен] [--count N] [--dry]
                                           [--email <id>] [--inviter <id>] [--minutes N]

Порядок головы: свободный ящик → `GET /api/verification?email=` → код из письма правилами
самого сайта (`main_site.mail_subject`, `code_anchor`, `code_length`, `code_format`, разбор
общий с `/api/mail/check-mailbox`) → `POST /api/user/register` с `aff_code` инвайтера →
`POST /api/user/login` → ключ → «Токен доступа» → запись через backend.

**Годность станции спрашивается у самой панели** (`gate()`), а не размечается в базе:
`register_enabled`, `password_register_enabled` и главное `turnstile_check`. Включённая
Turnstile — отказ на старте, а не попытка: без живой страницы токен капчи не получить, и голова
сожгла бы код на почте зря. Поэтому `ai.fujcloud.com` этим путём не берётся, а `api.hcnsec.cn`
берётся (капчи нет, `github_oauth` выключен вовсе).

Правила кода не зашиты в скрипт: у каждой станции своя тема письма и свой якорь, и заводит их
тот же человек, что заводит станцию. Пустой `mail_subject` или `code_anchor` — отказ на старте,
**но только у станции, которая код на почту требует**: без якоря регулярка вытащит из письма
первое подходящее число, а в письмах это id ссылки.
Письмо станции ложится в **спам**, и у ящика, уже гулявшего по станциям, там лежат прошлые
письма с той же темой — отсюда окно `CODE_WINDOW` (120 с) от начала ожидания.

**Станция может не спрашивать почту вовсе** — тогда цикл ещё короче: `email_verification: false`
у `qkmss.com` значит, что `POST /api/user/register` проходит с пустыми `email`
и `verification_code`, письма не ждём, а `SEND_GAP` уступает место `QUICK_GAP` (2 с). Признак
берётся из того же `/api/status` в `gate()` и живёт в `station["needs_code"]`; правила разбора
письма при `needs_code = False` не нужны и не требуются. Ящик из `main_email` при этом всё равно
берётся — но только под учёт, потому что индекс `(site_id, email_id)` требует своей строки
на голову; в записи `email` остаётся **пустым**, ведь у аккаунта на станции почты действительно
нет, а `note` это называет. Заглушки `no-email@warning.com` для новых голов больше не нужны:
их всего четыре, а ящиков пятьсот, и физически ящик здесь не расходуется — на другой станции
он по-прежнему свободен.

**Панель бывает нового вида.** У qkmss `POST /api/user/login` отдаёт не профиль, а
`{"user": …, "access_token": <JWT>}`, и дальше слушает `Authorization: Bearer <JWT>`, а не
cookie-сессию: `sign_in()` ставит этот заголовок в клиент сразу, иначе все следующие вызовы
получили бы 401 при полностью удачном входе. `/api/user/auth/refresh` (приём из GitHub-сбора)
здесь не нужен и отвечает `AUTH_UNAUTHORIZED`. `POST /api/token` без слеша отвечает 307,
поэтому путь пишется со слешем.

`SEND_GAP` (13 с) между головами — не вежливость: станция отвечает `发送过于频繁，请等待 12 秒`,
и лимит считается **по адресу**, а не по ящику, так что без паузы вторая голова кода не получит.

**Полное значение ключа отдаёт только `POST /api/token/<id>/key`**, и `data` там приходит
объектом `{"key": …}`, а не строкой: у первой головы 27.08 в базу уехал `sk-{'key': …}` и запись
пришлось править руками. «Токен доступа» снимается `GET /api/user/token` — эта ручка токен
не читает, а **перегенерирует**, гася прежний; на свежей голове это безопасно, на живом
аккаунте так отобрало бы доступ у балансера.

Партнёрская ссылка собирается с тем путём, что уже стоит у записи-инвайтера (`aff_path()`):
у hcnsec это `/register`, у qkmss `/sign-up`, а по HTTP путь не узнать — обе страницы отдают
одну оболочку SPA с кодом 200.

Партнёрский карман инвайтера переводится в баланс в конце прогона (`cash_inviter()`): 2000 $
за голову приходят в `aff_quota` и на запросы не тратятся, пока их не переложат, а балансер
сюда не заглянет — он ходит только по станциям с `meta.endpoints_anthropic`.

Автономность как у GitHub-сбора: `hold_lock("harvest_email")`, дедлайн `MAX_MINUTES` (13),
случайная выборка ящиков (`random.sample`), отчёт после каждой головы в `log/harvest_email.txt`
плюс дописывание в `log/harvest_email_history.txt`, построчный журнал
`log/harvest_email_journal.txt`, очередь `log/harvest_email_pending.json` под головы, которые
backend не принял по молчанию, — следующий прогон **начинает** с её дописывания. Ключ
и «Токен доступа» печатаются в отчёте целиком у всех незаписанных голов: повторно их взять
нечем.

В кроне две станции, и замок у них **один** — очередь и журнал общие, второй экземпляр вышел бы
молча, поэтому минуты разведены: `9,24,39,54 * * * *` для `api.hcnsec.cn` (`--count 10`,
прогон 5 минут) и `16,46 * * * *` для `qkmss.com` (`--count 3`). Вывод обоих —
`log/harvest_email_cron.txt`.

Проверено вживую 27.08: пять голов на api.hcnsec.cn подряд, все с 4000 $ старта, головы
по 15-20 с, инвайтеру (запись 100) капнуло 2000 $ за каждую и 10 000 $ переведены в баланс.
В тот же день две головы на qkmss.com — **7 секунд на обе**, записи 123 и 124, и свежим ключом
головы 123 живой `POST /v1/images/generations` отдал png на 1 МБ за 26 с: 500 бесплатных
генераций `gpt-image-2` даются аккаунту сами, отдельного погашения кода не нужно.

### Сверка аккаунтов с панелями по команде

`scripts/panel_sync.py` — ручной прогон под разделение труда, о котором просил Босс: он
вписывает то, чего в API нет (логин, почта, сам API-ключ `token`, «Токен доступа»
и «ID пользователя» со страницы `/profile`), а `balance` и `aff` скрипт заполняет сам
по `GET /api/user/self`. Идёт по обеим таблицам аккаунтов, берёт все записи с непустой парой
`access_token` + `panel_id`, кроном не запускается.

    uv run python scripts/panel_sync.py [домены станций] [--dry]

API-ключ здесь не заполняется намеренно: панель отдаёт его замаскированным
(`GQgq**********Gnof`) и в `/api/token/`, и в карточке ключа — полное значение видно один раз
при создании.

Партнёрская ссылка приводится к единому виду `https://<станция><путь>?aff=<код>`: у части
записей в базе лежал только код (`2PeJ`), а такой хвост без домена никуда не вставить. Путь
берётся из ссылок, которые Босс уже скопировал руками для этой станции (`aff_paths()`),
иначе `/sign-up`. По HTTP его не узнать: и `/sign-up`, и `/register` отдают одну и ту же
оболочку SPA с кодом 200.

Перед записью сверяется `display_name`/`username` из панели с `login` записи — токены
вставляются руками, и опечатка молча перепишет чужую строку. Отчёт —
`log/panel_sync.txt`, там же по станциям число приглашённых и партнёрский доход.

Тот же прогон правит `main_site.cnt` (`recount()`): считает записи по обеим таблицам аккаунтов
и переписывает счётчик, если разошёлся. Backend делает это сам на каждой вставке и удалении,
но записи, заведённые сырым SQL, идут мимо него — поэтому пересчёт нужен и здесь. Без фильтра
по домену прогон приводит в порядок все сайты сразу.
