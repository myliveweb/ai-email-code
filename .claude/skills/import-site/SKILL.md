# import-site

Босс ведёт учёт аккаунтов в текстовых файлах от руки. Такой файл — не CSV: разделители плавают, порядок строк меняется, рядом с данными живут его личные пометки. Задача скилла — превратить это в записи `main_site_account`, ничего не выдумав и ничего не потеряв.

Работа делится на две части, и они не равны по сложности. **Парсинг — это 90% работы**, и именно здесь ошибка дорого стоит: неверно извлечённый ключ или подхваченный из пометки мусор молча уедет в базу и всплывёт через месяц. Импорт после чистого разбора — механика на десять минут.

## Три правила, из которых следует всё остальное

**1. Данные — в начале строки, пометки — после `---`.** Формулировка Босса: «Обычно в начале строки идёт правильно то, что нужно в базу заносить, а потом уже хвостом прикрепляется, это как бы пометки, я сам для себя делал, и они как правило в базу не должны попадать». Поэтому строка сначала режется на `head` / `note`, и поля ищутся только в `head`.

**2. Пометка — не мусор, а тип значения.** Голый `boevhk51v` в списке-напоминалке и настоящий логин аккаунта выглядят одинаково; различает их только `--- GitHub`. Слова `bad` и `suspended` в хвосте — это правки для `main_github`. Так что из значения `note` вырезается, но читается как признак.

**3. Хвост, кроме суммы баланса, едет в `note` аккаунта.** Правило Босса от 2026-08-20: «Вообще в ноты заносите, кроме баланса, то, что написано после трёх тире». Причина в том, что из самих данных хвост не восстановить: тарифная группа ключа (`codex 0.015x-99%`, `claude`, `image`), назначение (`gpt-5.6-terra`), пометка `work` — «ключ уже используется в другом проекте». Без этого после импорта не видно, каким тарифом ходит ключ. Механика — `note_to` у поля с ключом плюс `note_clean` на уровне профиля, разобрано в `references/field-patterns.md`.

## Ход работы

### 1. Прочитать документ глазами

Открой исходник и посмотри 3–4 блока целиком, прежде чем писать регулярки. Нужно понять: чем разделены блоки, какие поля есть, как Босс помечает каждое, какие строки повторяются в каждом блоке (это шум), встречаются ли пометки брака.

Не начинай с кода. Формат рукописный, и пять минут чтения экономят три прохода парсера.

### 2. Написать профиль

Движок парсинга общий, под каждый документ пишется только профиль — JSON с регулярками. Профили лежат в `scripts/profiles/`, рабочий пример — `x-llm.net.json`.

Каталог проверенных паттернов для логинов, паролей, API-ключей, аффилятных ссылок и балансов — в `references/field-patterns.md`. **Читай его перед тем, как писать регулярку.** Там разобраны подвохи, которые уже стоили нам итераций: три похожие суммы в одном блоке, две партнёрские ссылки (нужна последняя), хвост после ключа без `---`, отличие логина от списка дублей.

Кроме регулярок в профиле есть четыре механизма, которые закрывают самые частые случаи без правки движка:

- `targets` — одна регулярка на несколько полей; группа 0 отдаёт всю строку. Так `login` = часть email до собаки, а `email` = вся строка, одним паттерном.
- `const` — константа на весь документ (общий пароль, дефолтный баланс), если поле ещё пусто.
- `dedupe_by` — Босс копирует блоки, и в конце файла нередко лежит побайтовая копия раннего. `["email", "token"]` отбрасывает повтор и печатает, какой блок какому был дублем.
- `overrides` — решения Босса по конкретным строкам, матч по значению поля (почта), а не по номеру блока.

### 3. Прогнать парсер

```bash
uv run python .claude/skills/import-site/scripts/parse_import.py \
    source/<file>.txt .claude/skills/import-site/scripts/profiles/<name>.json
```

Рядом с исходником появятся три файла:

- `_clean.txt` — блоки, разобранные без вопросов, готовые к импорту
- `_questions.txt` — блоки с неясностями, плюс их исходные строки с префиксом `# |`
- `_errors.txt` — найденные пометки `bad` / `suspended` для `main_github`

### 4. Показать Боссу вопросы, а не догадки

Это ключевой момент всего процесса. Когда паттерн не сработал, есть два пути: угадать или спросить. Угадывать нельзя — пароль или ключ, собранный из неверной группы, выглядит правдоподобно и проверке на глаз не поддаётся.

Поэтому блок с любой неясностью уезжает в `_questions.txt` вместе с исходными строками, и Босс закрывает вопросы одной-двумя фразами. В прошлый раз путь был 7 неясных блоков → 2 → 0 за три коротких раунда, и каждый раунд стоил Боссу пары предложений — потому что ему не приходилось открывать исходник.

Не отправляй Боссу больше вопросов, чем нужно. Хвост после `---` разбирать не надо — он его уже отбросил за тебя, и лишний вопрос про пометку раздражает: «Просто отбросьте этот хвост и действуйте как действовали со всеми остальными». Спрашивай только про строки, которые могли быть данными.

Дальше правь профиль и прогоняй заново, пока не станет `questions=0`. До этого импорт не запускай.

Ответы Босса записывай в профиль, а не в `_clean.txt` руками. Даже решение по одной строке («это ссылка от первого блока, ставьте прочерк») кладётся в `overrides` — тогда оно видно, воспроизводится при повторном прогоне и не теряется, если исходник придётся перечитать.

### 5. Импортировать

Порядок вставки, умная привязка, обработка `409`/`404` и применение пометок брака — в `references/import-flow.md`. Там же модель таблицы, индексы уникальности и рабочая команда для DDL.

Сам импорт делает `scripts/import_clean.py`: читает `_clean.txt`, шлёт записи с `smart_link: true`, печатает отчёт «вставлено N из M». Сначала `--dry-run`, потом `--limit 1` и проверка результата, потом остальные через `--offset`. Флаг `--custom` переключает на `main_site_account_custom` для документов, где регистрация шла не через GitHub.

Проверено на x-llm.net: 55 блоков, 55 вставок без ошибок, email у всех добран умной привязкой.
Проверено на tabitoken.com: 20 блоков, 17 чистых, 3 отложены по решению Босса, 17 вставок без ошибок.
Проверено на api.mhoo.cc: 21 блок, ни одного GitHub-аккаунта — 17 вставок в `main_site_account_custom` с привязкой по email.
Проверено на seekai.cc: 29 блоков, посреди документа маркер `GitHub` делит его на две таблицы — 14 вставок в `main_site_account_custom` и 13 в `main_site_account`, таблица тарифов ушла в `main_site.meta.price`.
Проверено на ai.fujcloud.com: 18 блоков, 18-й отброшен как дубль 4-го, 17 вставок в `main_site_account_custom` без ошибок; тарифные группы ключей приехали в `note` из хвостов.

## Чего не делать

**Не парсить документ вручную построчно в контексте.** Соблазн большой — файл на 900 строк читается целиком. Но результат нельзя воспроизвести, нельзя перезапустить после уточнения Босса, и второй документ придётся разбирать с нуля. Профиль воспроизводим и переиспользуем.

**Не писать значения в базу до `questions=0`.** Частичный импорт с включённой уникальностью придётся разбирать вручную: часть строк вставилась, часть упала на `409`, и непонятно, где остановились.

**Не выдумывать email.** Если его нет в документе — оставь пустым и добери умной привязкой. Backend найдёт его в `main_github` по логину.

**Не менять схему базы без явной просьбы.** База общая с другими проектами и агентами.
