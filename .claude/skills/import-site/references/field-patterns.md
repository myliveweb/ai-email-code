# Извлечение полей из рукописного текста

Каталог проверенных на практике паттернов. Копируй в профиль и подгоняй под конкретный документ, а не пиши регулярки с нуля.

## Главный принцип: head / note

Босс пишет данные в начало строки, а свои пометки — хвостом после `---`:

```
boevhk51v --- GitHub
sk-XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX --- много выбор ключей Codex 0.08x
aleksandrovna7rt9x --- bad
```

Движок режет строку на `head` (до `---`) и `note` (после). Поля ищутся в head, поэтому паттерн поля почти всегда можно закончить на `$` — хвост уже отрезан. Это сильно упрощает регулярки и убирает целый класс ошибок, где в базу протекала часть пометки.

Note не мусор: он несёт **тип** значения. Голый `boevhk51v` в списке дублей и настоящий логин аккаунта выглядят одинаково — различает их только `--- GitHub`. Поэтому у поля `login` стоит `note_regex`, и голые идентификаторы из списков-напоминалок отсекаются автоматически.

## Схема профиля

```
separator                 регулярка строки-разделителя блоков (по умолчанию 5+ '=' или '-')
note_marker               разделитель пометки, по умолчанию "---"
required                  какие поля обязательны; без них блок уходит в вопросы
                          (по умолчанию все)
ignore_bare_identifiers   гасить одиночные логины и e-mail без пометки, по умолчанию true
noise                     список регулярок служебных строк, которые молча пропускаем
note_clean                список регулярок, вырезаемых из пометки перед записью в note
dedupe_by                 список полей-ключей; повторный блок с тем же ключом отбрасывается
overrides[]               точечные правки по решению Босса: {"match": {поле: значение},
                          "set": {поле: значение}} — применяются после разбора блока
fields.<имя>
    regex                 паттерн по head (данные до note_marker)
    group                 номер группы со значением, по умолчанию 1
    targets               {поле: группа} — одна регулярка заполняет несколько полей;
                          группа 0 — вся совпавшая строка
    const                 {поле: значение} — дописать константу, если поле ещё пусто
    note_regex            поле сработает только если note подходит (регистр не важен)
    note_to               имя поля, куда положить саму пометку (обычно "note")
    note_if_missing       что писать, если пометки не было; по умолчанию "-"
    cast                  "float" | "int" | "lower"; float сам меняет запятую на точку
    on_repeat             "overwrite" (по умолчанию, последнее совпадение) |
                          "ignore" (первое) | "flag" (в вопросы)
    if_missing            что писать в отчёте, если поле не найдено
marks[]                   regex по head + note_regex по пометке + action для main_github
```

### Пометка как значение: `note_to`

Правило Босса от 2026-08-20: **всё, что стоит после `---`, кроме суммы баланса, надо занести в `note` аккаунта.** Причина простая — в хвосте живёт то, что из самих данных не восстановить: тарифная группа ключа (`codex 0.015x-99%`, `claude`, `image`), назначение (`gpt-5.6-terra`), пометка `work` («ключ уже используется в другом проекте»). Без этого после импорта не видно, каким тарифом ходит ключ.

Поэтому у поля с ключом ставится `note_to: "note"`, а сумма баланса вырезается на уровне профиля:

```json
"note_clean": ["^\\d[\\d\\s]*"],
"fields": {"token": {"regex": "^(sk-[A-Za-z0-9]{20,})$", "note_to": "note"}}
```

Хвост `7 000 default 0.13x -87% work` превращается в `default 0.13x -87% work`. Пометки-метки типа поля (`--- Access Token`, `--- GitHub`) в `note` тащить не надо — там `note_to` не ставится.

Если пометок несколько в одном блоке, они склеиваются через `; `.

### Дубли блоков: `dedupe_by`

Босс копирует блоки, и в конце файла нередко лежит побайтовая копия одного из ранних (на ai.fujcloud.com — блок 18 повторял блок 4). `dedupe_by: ["email", "token"]` отбрасывает повтор и печатает в консоль, какой блок какому был дублем. Ключ выбирай из полей, которые не могут совпасть у двух настоящих аккаунтов, — почта плюс ключ надёжнее одного логина.

### Решения Босса: `overrides`

Иногда строка неотличима автоматически, но Босс уже сказал, что с ней делать. На ai.fujcloud.com блок 5 начинался с аффилятной ссылки блока 1 — та же строка, тот же текст, отличается только положением, до которого движку не добраться. Решение («это ссылка от первого блока, игнорируем, ставьте прочерк») уезжает в профиль:

```json
"overrides": [{"match": {"email": "liamantoine31@gmail.com"}, "set": {"aff": "-"}}]
```

Матч по значению поля, а не по номеру блока: номера сдвигаются при любой правке исходника, а почта — нет. Это лучше правки отчёта руками: решение видно, воспроизводится при повторном прогоне и не теряется.


## Порядок полей в профиле

Движок идёт по полям сверху вниз и на первом совпадении останавливается. Поэтому **сначала специфичные паттерны, потом общие**.

Это не педантизм. Пара `login:password` описывается как «что-то, двоеточие, что-то» — и под это описание идеально подходит `https://some.site/signup?ref=AB12`: `https` + `:` + `//some.site/...`. Если пара стоит выше аффилятной ссылки, ссылка уедет в пароль, и в отчёте это выглядит правдоподобно. Рабочий порядок: URL и токены (у них есть префикс) → баланс (якорь `$`) → помеченные полем note → общие пары.

## Поля

### login аккаунта на сайте

```json
{"regex": "^([A-Za-z0-9._-]{3,})$", "note_regex": "^GitHub\\b", "on_repeat": "flag"}
```

`on_repeat: "flag"` — второй логин в блоке почти всегда означает, что разделитель блоков сработал не там. Лучше вынести блок в вопросы, чем молча взять первый.

Если в новом документе логин помечается иначе (`--- акк`, `--- login`, `--- reg`), расширь `note_regex` через `|`. Если пометки нет вообще и логин определяется только позицией — добавь якорь по соседней строке (например, логин идёт сразу после строки `Account`), для этого проще завести отдельное поле с паттерном по самой соседней строке, чем учить движок смотреть на контекст.

### email

```json
{"regex": "^([A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\\.[A-Za-z]{2,})$", "note_regex": "^(GitHub|email|mail)\\b"}
```

`note_regex` тут обязателен по той же причине, что и у логина: в блоках попадаются e-mail из списков «уже использовано» и адреса с пометкой брака (`--- bad`). Без note_regex они уедут в поле email.

Если email в документе нигде не указан — не выдумывай его. Оставляй пустым и добирай умной привязкой при импорте (`smart_link`), backend найдёт строку в `main_github` по логину и подставит email оттуда. Для читаемости отчёта задай `if_missing`.

#### Комбо-строки `email:пароль:секрет`

```json
"noise": ["^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\\.[A-Za-z]{2,}:"]
```

Строка вида `ivanova.ab12c@rambler.ru:PASSWORD:SECRET` — это не аккаунт на сайте, а данные от самого ящика: `main_email.email` / `password` / `secret` (формат rambler.ru). Босс выписывает их себе для входа в почту. На seekai.cc все пять таких строк совпали с `main_email` до символа, так что переносить из них нечего — гони в `noise`.

Дальше в блоке та же почта повторяется отдельной строкой, и под ней стоит уже пароль от **сайта** — он с почтовым не совпадает. Поэтому комбо-строку нужно не просто пропустить, а не дать ей испортить поле `email`: в паттерне email добавь lookahead `(?![:\w.-])`, иначе движок отбэктрекит TLD (`rambler.r` + `u`) и всё-таки сматчится.

### token / API-ключ

```json
{"regex": "^(sk-[A-Za-z0-9_-]{20,})\\b"}
```

Ключи почти всегда имеют узнаваемый префикс, и это самый надёжный сигнал в файле — привязывайся к нему, а не к длине. Встречающиеся префиксы: `sk-`, `sk-ant-`, `sk-proj-`, `sk-or-v1-`, `gsk_`, `ghp_`, `github_pat_`, `AIza`, `xoxb-`, `hf_`, `pk-`.

Не заканчивай паттерн на `$`: после ключа бывает хвост без `---` (`sk-xxx (осн)`). `\b` берёт ключ и игнорирует остальное.

Если префикс неизвестен, ориентир — «одна длинная строка из base64-алфавита, без пробелов»: `^([A-Za-z0-9_\\-]{32,})$`. Такой паттерн шумит, поэтому ставь его последним и обязательно прогони результат глазами.

### password

```json
{"regex": "^(\\S{6,})$", "note_regex": "^(pass|пароль|pw)\\b"}
```

Пароль структуры не имеет, отличить его от логина или мусора можно только по пометке или по позиции. Два рабочих варианта:

1. **По пометке** — как выше, если Босс подписывает `--- pass`.
2. **По паре в одной строке** — очень частый формат `login:password` или `login  password`. Одна регулярка отдаёт оба значения через `targets`, где ключ — имя поля, а значение — номер группы:

```json
"pair": {
  "regex": "^([A-Za-z0-9._-]{3,})[\\s:;|]+(\\S{6,})$",
  "targets": {"login": 1, "password": 2}
}
```

Имя самого поля (`pair`) в отчёт не попадает — в него идут имена из `targets`. Такое поле обязано стоять ниже URL и токенов, см. раздел про порядок: без этого партнёрская ссылка попадёт в пароль.

Если ни пометки, ни пары нет — не угадывай. Оставь строку в `_unknown`, она уедет в `_questions.txt`, и Босс объяснит одной фразой. Угаданный пароль хуже отсутствующего: он молча ляжет в базу и всплывёт через месяц.

### balance

```json
{"regex": "^([\\d]+(?:[.,]\\d+)?)\\s*\\$$", "cast": "float"}
```

Запятая как десятичный разделитель обязательна — Босс пишет `0,03`. `cast: "float"` сам меняет `,` на `.`.

Ключевой момент — `$` в конце: он отличает баланс аккаунта (`2 $`) от цены в рекламной строке (`41 моделей gpt-image-2 0,03 $`, где `$` тоже в конце, но строка начинается не с числа) и от бонуса в строке аффилятки (`?aff=B903 + 1 $`, где строка начинается с URL). Три похожие суммы в одном блоке, и разводит их только якорь начала строки.

### аффилятная (партнёрская) ссылка

```json
{"regex": "^(https://\\S*sign-up\\?aff=\\w+)\\b"}
```

Два подвоха, оба реальные:

- В блоке бывает несколько таких ссылок: первая — по кому регистрировались (родительский реферал), последняя — своя. Нужна **своя**, поэтому `on_repeat` оставляй по умолчанию `overwrite` — последнее совпадение вытесняет предыдущие.
- После ссылки идёт бонус (`+ 1 $`) без `---`. `\b` вместо `$` обрезает его.

Путь регистрации у разных сайтов свой (`sign-up`, `signup`, `register`, `ref`, `r`). Универсальный вариант: `^(https://\\S*[?&](aff|ref|r|invite)=[\\w-]+)`.

## Шум

Всё, что не поле и не пометка брака, попадает в `_unknown` и вытаскивает блок в вопросы. Чтобы отчёт не утонул, повторяющиеся служебные строки перечисляются в `noise`.

Что оказалось шумом в x-llm.net: имя сайта, ссылки `/pricing` и `/v1`, подпись `My Key`, рекламная строка про количество моделей, строки-пары `логин - email` из списков дублей.

`ignore_bare_identifiers: true` (по умолчанию) гасит одиночные логины и e-mail без пометки — те самые списки «уже использовано». Босс подтвердил: к импорту они отношения не имеют, а с уникальностью на уровне таблицы вообще потеряли смысл.

Не глуши шум заранее «на всякий случай». Сначала прогони парсер, посмотри, что реально попало в `_unknown`, и добавляй паттерны по факту. Иначе легко заглушить строку, которая была полем.

## Пометки брака

```json
{"regex": "^([A-Za-z0-9._%+-]+(?:@[A-Za-z0-9.-]+\\.[A-Za-z]{2,})?)$",
 "note_regex": "^(bad email|bad)\\b", "action": "Bad Rambler Email"}
```

Идентификатор берётся из head, слово-сигнал — из note. Один и тот же паттерн head с разными `note_regex` даёт разные действия. Порядок в списке `marks` важен: `bad email` должен стоять раньше `bad`, иначе более общий вариант съест более частный.

Пометки не относятся к импортируемому блоку — это правки для `main_github`. Они уходят в отдельный файл `_errors.txt` и применяются отдельным проходом. Что с ними делать — в `import-flow.md`.

## Как отлаживать профиль

Смотри `_questions.txt`: движок кладёт туда не только разобранные поля, но и исходные строки блока с префиксом `# | `. Этого хватает, чтобы понять, чего не хватило, не открывая исходник.

Блок уезжает в вопросы по двум причинам: есть `_unknown` или не заполнено одно из `required`. Второе чаще: одна строка, которую не поймал паттерн, — и весь блок в вопросах. Это правильное поведение, лучше пересмотреть блок, чем потерять поле.

Цель — `questions=0`. Пока не достигнута, импорт не запускай.
